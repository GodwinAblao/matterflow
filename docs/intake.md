# Matter creation and checklist setup

## Try a new workflow from scratch

1. Enter a demo as Staff and choose New matter on the Matters tab.
2. Enter a matter title, fictional client label, category, and initial document checklist. Include at least one required document. Optional items can remain missing without blocking readiness.
3. Create the matter. Its generated reference appears in the register and its checklist opens automatically.
4. Use Add requirement to extend the checklist before the matter is ready. Record receipts, switch to Reviewer, reselect the new reference, and accept or request corrections.
5. Once every required item is accepted, confirm readiness. The new matter and its actual records are included in analytics.

Reviewer creation can assign a workspace staff member. The Staff demo opens as Alex; choose Alex when testing a complete receipt/review cycle. Assigning Sam demonstrates workload distribution and staff read restrictions. There is no production identity login in this portfolio prototype.

## Permissions and validation

Staff can create only matters assigned to themselves. Reviewers may assign a staff identity from the same workspace; external or nonstaff identities are rejected. Assigned reviewers are chosen from the current workspace on the server. The browser cannot supply another workspace or set initial document statuses.

Matter titles contain 1-200 characters; fictional client labels contain 1-120. Creation accepts 1-20 checklist entries, at least one required. Checklist titles contain 1-200 characters, are normalized for whitespace, and cannot repeat ignoring case. Matter references are generated by the backend, not entered by the browser.

Assigned staff and reviewers may add requirements to accessible nonready, nonclosed matters. Each addition requires the displayed matter version, checks for duplicate titles, and uses the same matter lock as readiness confirmation. At most thirty checklist entries are supported per matter. Existing requirements cannot be removed or downgraded through this feature; this preserves the review history and prevents weakening a checklist after review.

A demo workspace supports fifty matters, including its initial twelve examples. The generated references continue from MF-013 on an unchanged seeded workspace. Creating an intake matter, its initial requirements, and its opening activity uses one PostgreSQL transaction.

## Creation retries and reference allocation

Each request carries a random UUID creation_key. The frontend retains that key when a request fails and renews it when the draft changes. The backend stores the key and a SHA-256 fingerprint of the normalized payload in the new matter. Retrying the same request returns the existing ID/reference with replayed=true; reusing a key with changed content returns 409. Keys are unique within a workspace.

A workspace-specific PostgreSQL advisory lock serializes creation requests before authorization row locks. It protects both the reference counter and the matter limit without upgrading shared row locks. Distinct concurrent requests receive distinct references; duplicate concurrent retries create one matter and one opening event.

Additional requirement requests use optimistic matter versions instead of creation keys. Adding a required item and confirming readiness cannot both succeed from the same old version. Either the added item blocks readiness, or readiness completes first and further additions are rejected.

The fifth migration adds nullable creation metadata to matters. Seeded matter rows leave these fields empty. Request bodies are limited to 32 KiB to accommodate the bounded initial checklist, including Unicode text.

## API

- GET /api/v1/matters/options: staff assignment choices, scoped to the current role/workspace.
- POST /api/v1/matters: creation_key, title, client_label, service_category, optional assigned_staff_id, and documents containing title/is_required.
- POST /api/v1/matters/{id}/requirements: expected_version, title, is_required.

New matters return 201; successful creation retries return 200. Requirement additions return 201. Validation errors return 400, role violations 403, unknown/inaccessible resources 404, and stale versions or creation-key misuse 409. Unknown fields and invalid enums/UUIDs are rejected during JSON parsing.

## Verification

Run npm.cmd run test:intake against the migrated and seeded development database. The tests create isolated workspaces and remove them on success. They verify new matter creation through acceptance/readiness, workspace ownership, required/optional flags, activity creation, invalid and duplicate titles, assignment restrictions, repeated requests, concurrent reference allocation, stale checklist writes, and the requirement/readiness race.
